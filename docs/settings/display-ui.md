# Display & UI settings-domain contract

This is a clean-room, no-device, metadata-only MVP contract. It proposes semantic settings for a parent registry/menu descriptor; it is not a global settings schema and does not claim a device, panel, battery source, input source, firmware behavior, HAL implementation, or Artbook runtime.

## Requirements

Defaults are safe persisted preferences unless marked unavailable. A value described as `unset` means no explicit preference and is always valid; an opaque option is valid only when the consuming capability advertises it.

## Transaction and menu behavior

- A menu edit validates the edited field and any related fields before application. A failed validation leaves persisted values and current confirmed UI state unchanged.
- Immediate settings apply only after validation and have no pending confirmation state.
- Deferred settings expose a pending candidate until the next safe UI transition. A menu may show that candidate as **pending confirmation**; `confirm` commits it and `cancel` restores the last confirmed value. An unconfirmed candidate is not persisted.
- The only cross-field rule in this MVP is `dim_timeout < screensaver_timeout` when both are finite. `screensaver_timeout = disabled` removes that comparison and does not disable an independently finite dim timeout.
- Reset restores each setting's contract default. For `display.brightness`, reset produces unavailable/no value unless the capability gate is currently satisfied; reset never probes or invents a range. Reset of a disabled dependent setting does not make it visible: `display.battery_presentation` remains unavailable while `display.show_battery` is `false`.
- Unsupported capability options and invalid values are rejected before persistence or runtime application. There is no partial application across a multi-setting edit.
- No setting is secret or personally identifying, and this contract defines no telemetry.
