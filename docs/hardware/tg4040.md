# TrimUI Brick Pro TG4040 provisional hardware/BSP contract

## Scope and evidence boundary

This is the authoritative **no-device provisional** contract for the exact `TG4040` target. It defines the facts and safe defaults that a future hardware support layer may use; it is not a HAL, HIL runner, firmware package, or device implementation.

The contract was prepared without a physical device. Its official inputs are only the three pinned GitHub release assets recorded by the evidence index:

- firmware release `v1.1.1-20260717`, commit `08cb7b5c92ea6b0df5f43f1bc66334f351a3f6eb`, from [`trimui/firmware_brickpro`](https://github.com/trimui/firmware_brickpro/releases/tag/v1.1.1-20260717);
- assets release `v1.0.0-20260626`, commit `18182893374a412d36fe541a1c55b4838616f7a4`, from [`trimui/assets_brickpro`](https://github.com/trimui/assets_brickpro/releases/tag/v1.0.0-20260626).

The index and sanitized archive inventory are the only checked-in evidence. No archive entry names, extracted bytes, source, configuration, scripts, artwork, binaries, private data, or raw listing is redistributed here. Existing simulator documentation remains a state-only test-double boundary, and the existing provenance policy continues to block redistribution of stock/vendor material.

The only permitted fact statuses are exactly `verified`, `stock-derived`, and `unknown`:

- `verified` requires a later observation from a physical TG4040 and is not used by this no-device baseline;
- `stock-derived` is a narrow fact about the pinned official release metadata or sanitized inventory, never a runtime assertion;
- `unknown` means the evidence is insufficient and the implementation must fail closed.

An archive being present, readable, or named for TG4040 does not prove that a device boots it, that it runs a particular kernel, or that any hardware backend exists.

## Fatal target gate

Every hardware-facing entry point must first obtain a readable identity whose SKU is exactly `TG4040`. Missing, unreadable, contradictory, malformed, or differently identified data fails closed. The gate runs before opening a device node, loading a backend, invoking a daemon, selecting a mapping, or writing persistent storage. There is no fallback target and no inference from a release filename.

| Candidate | Treatment |
| --- | --- |
| TG4040 | The sole target of this contract; proceed only after the exact identity gate passes. |
| TG3040 | Excluded, not a compatible target; no evidence, mapping, artifact, or fact is carried across. |

## Conservative software defaults

Until the relevant capability is proven on a physical target:

- perform no raw hardware access and invoke no vendor daemon;
- return an explicit unsupported/error result for unsupported operations;
- do not assume mount paths, kernel ABI, input event numbering, display format, radio stack, USB role, or persistent-storage safety;
- do not probe by side effect and do not write eMMC, partition, or block devices;
- treat absent, malformed, stale, or contradictory capability evidence as failure, not as permission to guess.

This contract intentionally leaves implementation choices open. It does not authorize a HAL, HIL, simulator change, flashing, device probing, or performance claim.

## Later on-device verification procedure

A later `verified-on-device` upgrade is a procedure, not a fourth status:

1. verify the physical identity gate and record an exact TG4040 observation before touching any backend;
2. collect the smallest necessary observation for one fact, with command, timestamp, operator context, and integrity metadata kept outside the repository when sensitive;
3. review it against the pinned release boundary and reject contradictory or target-ambiguous observations;
4. add only sanitized, reproducible evidence metadata and an index ID; never copy device dumps or private identifiers;
5. change that fact's status to `verified` only after review, retain `unknown` for every untested claim, and rerun `scripts/check-hardware-contract` plus the relevant hardware validation.

Physical closure is explicitly deferred to Kanban cards `t_d3ef25c0` and `t_092a77c1`. No physical TG4040 result is claimed here.

## Evidence records

The evidence IDs in the fact table resolve in [`index.json`](evidence/tg4040/index.json). Each archive attempt locally matched the published byte count and SHA-256 before listing. The sanitized inventory records only counts, broad entry types, the method, and a hash of each full external inventory; the full external listings remain outside the repository and are not content evidence.
