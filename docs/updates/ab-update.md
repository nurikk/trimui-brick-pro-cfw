# A/B userspace updates

`update-agent` is the single TG4040 updater for both online and sideloaded packages. The caller obtains the manifest and payload from the manifest's HTTPS `artifactUrl` for `--source online`, or selects the same two files from removable storage for `--source sideload`; both sources enter the same preflight, staging, activation, and rollback path.

Before boot state or either slot is changed, preflight requires the exact device ID, TG4040 SKU, hardware revision, active source release, stock-firmware window, userspace ABI, data-schema window, SquashFS type, payload filename, byte size, SHA-256, three-copy peak free space, and either external power or at least 50% battery. The closed user-data manifest contains exactly saves, credentials, achievements, mappings, Fn/LED settings, service settings, and emulator selections. Those shared `/data` paths are checksum-checked and use the existing copy-on-write, prior-release-readable migration contract; ROMs remain outside updater ownership.

The payload is copied to `.brickpro/data/update/staging/<release-id>`, verified again, copied to the inactive `.brickpro/system/slots/{A,B}` slot, and verified again before `prepare_pending` publishes boot state. Synced temporary files and atomic renames make rerunning the command safe after interruption. The generic `.brickpro/data/update/status.json` UI record shows current and target release, online or sideload source, current stage, progress, actionable error, and a bounded journal of preflight, download, unpack, apply, first-boot, completion, error, and rollback transitions.

First boot gets three health-gated attempts. Failure automatically selects the previous slot. A successful first boot keeps **Restore previous release** available: Recovery runs `brickpro-boot-state rollback --root <card-root>`. This changes only A/B selection; it does not format, delete, or modify the ROM library, so recovery does not require destroying the ROM card.

Release packaging remains an ordinary deterministic tar archive with `manifest.json`, the named payload, and the generic online/sideload/previous-slot action record. SHA-256 and transactional recovery are the trust boundary; signing, PKI, provenance, and anti-rollback are intentionally out of scope.
