# System & Maintenance settings domain

## Status and boundary

This is a clean-room semantic-domain proposal for a future generic settings registry and automatic menu generator. It suggests stable semantic IDs and metadata values; it does not define the global descriptor/schema format, serialization, UI, updater, formatter, HAL, or destructive implementation.

The domain is logical and no-device. `/system` is read-only, `/data` is CFW-owned, and `/roms` is user-owned discovery-read-only. Device- or system-dependent capability evidence is valid only when present, well-formed, fresh, internally consistent, and explicitly supported by a future owning contract. Absent, malformed, stale, contradictory, or unsupported evidence fails closed. No row authorizes a guessed mount, runtime, entrypoint, device path, physical power chain, stock chain, filesystem behavior, ABI, loader, update path, or hardware operation.

Actions below are candidates. A registry may expose an action only when its capability gate passes and its owning implementation separately validates inputs and boundaries. Legal and provenance information is display-only. Diagnostics must be bounded and sanitized: never include ROM/BIOS bytes, names, paths, hashes, or private credentials.

## Required semantic invariants

- `/system` remains read-only; `/data` is the only CFW-owned settings boundary; `/roms` remains user-owned discovery-read-only.
- Update handling is limited to channel preference and the non-mutating check candidate. No release bytes or release state may be downloaded, installed, activated, rolled back, migrated, or written by this domain.
- Safe mode is a pending next-boot request only. A failed or unsupported persistence operation must not claim that it was scheduled.
- Reset UI settings cannot cross into typed non-UI settings. Reset all CFW settings requires explicit confirmation and has a cancel path with no changes; both reset actions exclude user ROM/BIOS content, saves, states, credentials, provenance records, release/system content, and hardware/storage operations.
- Power/restart and stock passthrough remain request/status candidates. Unknown or unavailable status stays visible and keeps actions unavailable.
- Notices and provenance are display-only and do not imply license approval, redistribution permission, legal advice, or distribution of bytes.

This proposal intentionally leaves registry/schema shape, persistence encoding, menu rendering, action execution, and device validation to their owning contracts.
